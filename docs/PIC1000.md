# Sony PIC-1000: ROM damage and reconstruction findings

The only known PIC-1000 dump (`PIC-1000.rom`, SHA-256
`01d779982b47d233dbb670375663f705c9161a3c0e0a2d9c7b4feda8178efef3`) is
damaged. MagicHat identifies it (see [ROM_DETECTION.md](ROM_DETECTION.md))
but has no runnable board for it. This page records what the damage is,
and what a donor-based reconstruction established. No reconstructed image
is distributed or supported; the findings are recorded so the work need
not be repeated from scratch.

## Checksum failure

The ROM header selects bytes `[FB8,2E32BC)`; their byte sum is
`0DE87511`, while the stored checksum at offset `4C` is `0DD2BE2B`. The
guest computes the same sum and fails its own assertion at `0E000D76`.

Changing only the checksum field lets execution continue, but it fails
soon after. Cold execution calls selector `029D` from
`0E07E464..0E07E468`; the dispatch trampoline at `0000025E..266` resolves
it to `0E088190`, and the CPU reaches illegal opcode `0E00` at `0E088196`
(instruction 9,721,114). Vector 4 enters the reset-time BGND handler at
`0007FFF8`. The file bytes at `88190` are:

```
0100 0004 8000 0E00 0000 0680 0000 FF80
0001 0080 0003 2F01 A080 8CF0 0000 000C
```

These are bytes in the image, not RAM corruption.

## Damage model

For every aligned four-byte group, compare the first halfword with the
first halfword one MiB away (address bit 20 toggled). In the first lane
all 524,288 pairs match; in the second only 4,649 do. Measured further,
the alias is exactly one shorted address line, not a stuck one: for the
first halfword of every aligned 32-bit word (the high-halfword ROM chip),
the byte at file offset X holds the byte from **X with bit 20 := bit 19**.

- Lane 0/1 is intact where bit 20 == bit 19: `000000-07FFFF`,
  `180000-27FFFF`, `380000-3FFFFF`.
- Lane 0/1 is **lost** where they differ: `080000-17FFFF` and
  `280000-37FFFF` (four 512 KiB regions, 1 MiB of halfwords).
- Lane 2/3 is intact everywhere.

Per-256K-block LINK A6 / RTS statistics support this: blocks the model
calls intact have 93-96% valid LINK immediates in both lanes; blocks it
calls damaged have 0-21%. Bits 21 and 19 do not alias. HIX-300 does not
show this pattern ([HIX300.md](HIX300.md)).

No independent dump is known. The checksum cannot uniquely recover the
lost bytes, and the Magic Cap Macintosh simulator's 68k code gave no
eight- or sixteen-word exact matches around the failing entries, so it is
not a donor for specific words either.

## Donor reconstruction

The other 68k ROMs share the Magic Cap 1.x code base: in intact regions,
60-68% of sampled 32-byte runs of PIC-1000 appear verbatim in PIC-2000 and
up to 87% in Envoy 1.0. Because every second halfword survives in the
damaged regions, donor code can be aligned at halfword granularity and the
lost lane filled from it. The approach and what was measured:

- **Alignment.** Each donor (Envoy 1.0, PIC-2000, HIX-300) is aligned by
  runs of matching surviving halfwords (seed 4 words, run of at least 6,
  small holes merged). Envoy covers 98-99% of the damaged code regions;
  the data-heavy regions `140000`, `2C0000` and `340000` are covered poorly
  by every donor. Envoy addresses its ROM at `0040xxxx` as well as
  `0240xxxx`.
- **Voting.** Lost halfwords are filled by majority across donors,
  weighted by method: a halfword copied from inside a verified run beats a
  donor opcode borrowed for a PC-relative reference whose target differs
  (1076:0 on intact regions). Aligned ROM pointers are translated and
  checked against the intact low halfword.
- **PC-relative displacements** (Bcc.W, `JSR/LEA d16(PC)`) are solved from
  the callee the donor reaches, mapped back: directly when in range,
  otherwise via a `BRA.W` island chain. Far calls go through chains of
  linker islands (20 hops for memcpy in Envoy) placed differently per
  build, so an island's displacement is constrained by its callers, never
  by the donor's island at the same position.
- **Seams.** Where one donor run ends and another with a different delta
  begins at the same group, the side on which the inserted bytes decode as
  whole instructions decides (right 45:1 on intact seams); otherwise the
  later run wins (49:1).
- **Short branches** (`Bcc.S`) are re-encoded only when the branch sits in
  a verified run and the bytes it skips decode as whole instructions.
- **Validation.** Treating intact regions as damaged and scoring the
  result: **1.63% of filled halfwords wrong**, mostly genuinely different
  hardware/RAM constants and single-donor Envoy fills.

### The object index, recovered without donors

Magic Cap keeps its ROM-resident objects in one contiguous heap followed by
an index: one 32-bit entry per object number,
`0x80000000 | (object offset - descriptor)`. A page descriptor, found by its
fixed fields, gives the table position and object count. Both heap and
table lie in the damaged range, so every entry lost its high halfword.

They come back exactly because **each object names itself**: the long at
object+8 is `(flags << 24) | object number`, and its surviving half holds
the number. An object at offset O claiming index i is credible only if the
surviving half of entry i equals `(O - descriptor) & 0xffff`, about one
chance in 500,000. The survivors tile the heap contiguously, which settles
the dozen positions that alias (they differ by exactly `0x100000`). This
reads only the intact lane. Scored on undamaged ROMs:

| ROM | Entries | Recovered | Correct |
| --- | ---: | ---: | ---: |
| PIC-2000 | 10,355 | 10,353 | 10,353 |
| Envoy 1.0 | 9,234 | 9,233 | 9,233 |
| HIX-300 | 9,054 | 9,049 | 9,049 |

No wrong answer in 28,635 entries. On PIC-1000 it recovers 9,227 of 9,228
objects and, with them, each object's size field: 10,654 halfwords.

### Class method tables

A class body (object + 0x10) holds a superclass count at +0x08, the
superclass list offset at +0x0A, a method count at +0x0C and the method
table offset at +0x0E. The table is an array of 16-byte records
(selector, code offset, flags, owner) sorted by selector for binary
search. On a 4-aligned PIC-1000 object the counts are lost and the offsets
survive. Four fields follow from the format, each checked against every
class in the three undamaged ROMs:

| Field | Rule | Checked |
| --- | --- | --- |
| selector high half | always `0x0000` | 10,404 records |
| owner high half | `0x8000` exactly when its low half is non-zero | 10,404 records |
| method count | `(object end - table start) / 16` | 703 classes |
| superclass count | `(method offset - superclass offset) / 16` | 703 classes |
| superclass entry | four longs, every high half `0x0000` | 737 entries |

Code pointers need donors. A class is matched to its donor counterpart by
its surviving selector list (Envoy 1.0 matches 227 of PIC-1000's 231
classes exactly), and the donor's code offset is mapped through the
alignment; the surviving low halfword then selects the high half nearest
the mapped target. Envoy alone was right 289 of 289 times on records whose
high half survived; with all donors and a nearby-run fallback, 2,137
records were decided at 19 wrong in 323 checkable. Classes are found by
testing for sorted, mostly distinct selectors at the table offset; on
undamaged ROMs the derived counts equal the stored ones for every class
found (246, 232 and 225). Filling unmapped records from the modal page of
their class (3 right, 137 wrong) and matching method bodies by donor code
bytes (4 of 3,539 decided) were rejected on measurement.

## Boot status reached

With all of the above, 435,284 halfwords were filled and 89,004 lost
groups (17.0%) stayed unresolved. By region: `080000` 0.4%, `0C0000`
0.1%, `100000` 0.3%, `140000` 41.8%, `280000` 12.6%, `2C0000` 7.3%,
`300000` 1.4%, `340000` 71.8%. Coverage over 100 million instructions, in
distinct 256-byte blocks:

| Stage | Blocks | How it ends |
| --- | ---: | --- |
| First donor fill | 50 | retries a send forever, no exception |
| + seam/branch rules | 58 | wild jump at 15.5M |
| + object index | 244 | wild jump at 15.5M |
| + class tables | 2,087 | runs the full 100M, in an error loop |

PIC-2000 reaches 1,631 blocks on the same budget, so the reconstruction
executes more of its ROM, including much error handling. The built-in init
(`0x260`, `0E07E414`) now runs to completion; a control-flow trace diff
against PIC-2000's copy agreed for 18,654 events and then differed only in
a delay loop's iteration count. Selector `0x1238` on object 3, which
installs the low-RAM trampolines, dispatches to the installer at
`0E04AA30`.

The display works: DRAM `0x2800` after 100M instructions shows the
vertical-bar display self-test, not the splash. The first failure is a
send of selector `0x10` to object `0x84001A28` (class at `0E1586F0`) that
resolves to address 0 at 15,471,977 instructions; that class's own table
matches Envoy exactly, so the method is missing further up the chain.
1,066 of 3,539 method records still had code pointers the donors could not
place.

A reconstruction of this kind is a declared derivative, not an
authenticated dump: wherever a halfword came from a donor, it is the
donor's byte. Execution progress does not prove any inferred word correct.
Remaining leads were the unplaced method pointers (extending alignment
around method bodies), unsolved PC-relative sites, and the largely aliased
data regions `140000` and `340000`.
