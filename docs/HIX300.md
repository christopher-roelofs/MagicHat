# Sony HIX-300 bring-up

The ROM identifies as Magic Cap 0.19 (`1,0.19,SONY,1,`). It reaches the
Desk with checksum recovery and the default, inferred HIX audio-divider
model, and its welcome message reads **Version 0.19 MC19 C2 for Bamboo**.
The launcher routes detected HIX ROMs to the 68k machine; `--device hix300`
also selects it explicitly. Hardware validation remains incomplete. Use
fresh temporary RAM while testing.

```sh
./build/mhat --rom roms/hix300-mc19-c2.rom --fresh --temporary
```

No audio-divider flag is needed for identified HIX ROMs. The image supports
an external Magic Bus keyboard through the ROM's ATKB driver; see
[68k keyboards](68K_KEYBOARD.md) for the distinct HIX input pin, legacy
command header, and validation.

## Integrity check

The `hix300-mc19-c2.rom` image fails its startup byte-sum check:

- Checked file bytes: `[0xC8E,0x2AF08E)`.
- Stored checksum at `4C`: `0CA6B70B`.
- Actual sum: `0CA6B374` (lower by `397`, decimal 919).
- SHA-256:
  `2779a88b7b3e2cf35aaf5eb1debfa742c81fd10668ee96d0cf2eb7b7344192d6`.

The machine prints a warning at ROM load when these sums differ, including
both values and the checked range. At the user's request, identified HIX
images with a mismatch automatically enable a guarded checksum-result
interception. The instruction bytes at `A7C..A91` must match the known
call/comparison/failure/success sequence; otherwise interception is
refused. At PC `0E000A82`, A4 must be `0E00000C` and D0 must equal the
independently calculated sum. The hook then substitutes the stored checksum
in D0, allowing the normal CMP/BEQ success path. Startup and each actual
interception print a `DEVIATION` message. ROM bytes remain unchanged on
disk and in memory. Matching-checksum images do not enable the hook.

This is an explicit, user-requested recovery exception to the normal
no-guest-interception methodology (see [METHODOLOGY.md](METHODOLOGY.md)).
It does not repair unknown ROM damage. The CLI test covers interception,
refusal of changed instructions, and a matching checksum, and verifies that
the input file is unchanged. Envoy mc31 uses the same mechanism; see
[ENVOY.md](ENVOY.md).

At `0E000A82` the CPU's result exactly matches the independent file sum.
Without recovery the failure returns error `16` at `0E000A88` before
constructing the dispatch vector. The outer reset code nevertheless calls
`-6(a5)` with A5 still `0E000000`, which explains an early wild jump to
`0DFFFFFA`. That jump is a consequence of the failed checksum, not evidence
of a missing ROM mapping below `0E000000`.

Unlike PIC-1000 ([PIC1000.md](PIC1000.md)), neither halfword lane repeats
wholesale across address bit 20. This does not prove the rest of the file
correct, and the mismatch itself remains unexplained. A checksum-only
patched copy was also tested during bring-up; the runtime recovery makes it
unnecessary.

## Startup audio

After the checksum, the ROM reaches the startup speaker/DMA test at
`0E077C64`:

- It fills RAM at `12000` and programs audio buffer register `50=0012`.
- It writes rate register `52=05A0` and starts playback with `4E=1007`.
- It waits at `0E077C9C..CA4` for B0 word bits `000C`, the same DMA
  boundary sources used by PIC playback.

The PIC audio decoder ([PIC2000_AUDIO.md](PIC2000_AUDIO.md)) knows
`D20/C30/B40/A50/950/960`, but not `05A0`, so without a divider model it
consumes no buffer and generates no completion event. HIX's normal
rate-selection function at `0E077CBC` uses the familiar six encodings;
the startup test explicitly chooses `05A0`.

HIX also programs CS3 base/control `1E0000F1` and writes its speaker output
latch at `1E000000` (`0E077D82`). The board maps its auxiliary register
file there instead of PIC's `0C000000`. The latch is a reported register
file, not a fully understood peripheral.

## Inferred divider and successful boot

The HIX board defaults to an inferred counter interpretation of the two
middle nibbles: ticks = `(high - low + 1) mod 16`, with zero meaning 16,
and sample rate = `88200 / ticks`. All six established rate codes fit this
formula; `05A0` then gives 7,350 Hz. Neither the counter interpretation nor
the 88,200 Hz clock is confirmed by a hardware specification. At the
user's request it is the default for identified HIX ROMs and prints an
unverified-timing notice at startup. Other boards keep their defaults;
`--experimental-audio-divider` enables the hypothesis explicitly for them.
Rates above the engine's 44.1 kHz sampling rate remain unsupported.

With this model, real buffer consumption produces the DMA boundary event
and startup proceeds; no forced completion bit or guest-memory patch is
used. A 190-million-slot replay with four taps reaches the Desk and its
welcome message. This establishes progress through onboarding, not full
hardware accuracy.

## Display

HIX clears 38,400 bytes starting at RAM `8000` at `0E05D8D4`, and programs
LCD register `21000048=2000`. PIC programs `0A00` for RAM `2800`. The
frontend reads the programmed base in four-byte units instead of always
using PIC's buffer. Both use the same 480x320, 2-bit pixel format. A
runtime fixture verifies that changing the register selects the new buffer
and preserves pixel ordering.

```sh
./build/mhat --device hix300 --rom roms/hix300-mc19-c2.rom \
  --fresh --temporary --headless -n 190000000 \
  --tap 90000000,1000000,240,160 \
  --tap 120000000,1000000,23,23 \
  --tap 145000000,1000000,456,297 \
  --tap 170000000,1000000,240,160 \
  --dump 8000,38400,hix-calibration.fb
```

## Power input and retained-memory startup

HIX's power input behaves as a latched ON/OFF level:

- `0E054D24` reads `210000D1` bit 2 as the current power input.
- `0E054CCC` clears B8 word bits `000C` and enables the falling-edge source
  (`C0` word bit `0004`).
- The edge dispatcher at `0E054C1E` delivers the level to object
  `8705A019`.
- Its method at `0E054D4E` requests shutdown when that level becomes false.

A momentary launch press therefore switched HIX back off when released;
extending the press only delayed the shutdown. This was most visible on
retained-memory boot, which displayed SONY or briefly restored the Hallway
before switching off.

HIX now starts with its power input latched ON. F4 toggles the input on
each new key press; key release and repeat leave the level alone. Closing
the GUI toggles it OFF through the guest shutdown path. PIC and Envoy keep
their momentary-button behavior. This board wiring is inferred from ROM
behavior, not a verified physical switch specification.

The CLI regression checks that startup remains ON beyond the old release
deadline and that a scheduled press switches OFF without its later release
switching ON again. A retained session stayed awake for 1 billion slots
(about 59.6 emulated seconds) with zero visits to shutdown entry
`0E05D6FA`; a separate run toggled OFF at slot 300 million and reached
that entry at slot 309,718,367.

## Held-pen sampling and modifiers

Pen contact does not assert `210000D1` bit 1: that is the Option-key input,
as established through the SDK HardwareOptionKey intrinsic and the ROM
(see [ENVOY.md](ENVOY.md)). Shared code had previously turned normal drags
into Option-drags.

The inferred two-conversion X/Y acquisition under mux `69`, channel zero,
resets when the guest starts another selector or channel. Host pointer
movement updates sensor values without resetting acquisition phase or
changing an already-latched conversion, so subsequent acquisitions return Y
correctly. Register tests exercise motion between conversions and repeated
acquisitions; the CLI test checks that contact leaves Option off.

Normal mouse movement does not write per-channel ADC diagnostics on every
motion event. Explicit ADC injection still reports its overrides, and
`MH_TOUCH_TRACE=1` enables motion coordinate tracing.

## SDL pen queue

The shared 68k SDL frontend used to apply all pending mouse events before
executing the guest, so a delayed poll containing down/motion/up could
overwrite the initial point before the guest sampled it. Replaying every
host timestamp instead built up stale movement when emulation fell behind.

The live queue now keeps press/release edges and only the latest pending
motion, and splits execution at queued pen deadlines so initial contact is
sampled before motion and release. New events have a deadline no earlier
than the current guest slot, and no later than one 60 Hz sampling interval
ahead; coalescing an overdue motion advances its deadline to the current
slot, while a future pending deadline is kept to prevent starvation.
Release preserves the minimum tap hold and gives the final position one
sampling interval. Guest clocks and CPU speed are unchanged.

Queue tests cover delayed whole-gesture batches, late motion/release after
a consumed press, 999 motion updates without guest progress, timestamp wrap
and stale timestamps. A dummy-driver SDL replay through the old frontend
applied final motion and release at the same slot (49,155,645); the
corrected frontend applied them 279,620 slots apart (one 60 Hz interval).

## PIC-2000 comparison: displacement rejection

HIX `0E0608EC..0E060908` rejects a held sample if either axis differs from
the **last accepted** raw coordinate by more than `0x64` (100). PIC
`0E08BC2A..0E08BC42` uses `0x12C` (300). A rejected HIX sample restarts
acquisition without advancing the last accepted point, so holding at the
distant new position never makes the next sample acceptable. With retained
HIX calibration X endpoints 138 and 966, 100 raw units are about 57.9
screen pixels. This is a per-sample jump limit, not a limit on total drag
length.

Controlled runs held Y=260 after booting each retained session for 100
million slots. Smooth movement used 5-pixel steps held for 279,620 slots
(about 16.7 ms); the jump test changed X directly from 160 to 260.

| Input | HIX hallway movement | PIC hallway movement |
| --- | ---: | ---: |
| Gradual 200-pixel drag, away from end stop | about 200 pixels | 200 pixels |
| One 100-pixel jump during a held contact | 0 pixels | about 100 pixels |

A first rightward HIX test moved only 88.117 pixels because scene
coordinates stopped at a boundary (RAM `19FA0` went from `000007E2` to
`00006000`); later comparisons start from an interior position. In the
smooth trace all 42 held samples reached accepted-sample entry `0E06090C`,
with raw differences of 0, 8 or 9 units. Other firmware differences did not
cause that run: HIX has 16 motion entries and doubles its requested
interval on overflow (up to 250 ms, `0E0609FC`); PIC has 32 and selects
10 or 20 ms by occupancy. HIX's initial request is 20 ms, PIC's 10 ms.

HIX countdown setup at `0E06035C..0E060376` encodes a nonzero millisecond
request as `((request + 7) >> 3) - 1`; PIC at `0E08B710..0E08B724` uses
`(request + 8) >> 3`. The shared model uses `max(count, 1) * 8 ms`. Neither
convention alone establishes the hardware terminal-count semantics, so no
timer change was made.

## Bounded frontend pen trajectory

To keep coalesced host movement from becoming one large sensor jump, the
shared 68k SDL frontend delivers movement through intermediate positions:
at most 16 panel pixels per axis every 1/120 guest second. It keeps one
motion destination between contact edges; new movement retargets from the
last delivered point, so a reversal does not first finish the obsolete
destination. It neither patches the ROM filter nor changes CPU, timer or
converter clocks. This is host input translation, not a verified physical
digitizer response.

Small movements arrive in one update. A full-width jump takes roughly
250 ms of interpolation (under 284 ms total in the whole-batch test).
Release waits for the final destination and one further 60 Hz interval as
well as the minimum contact hold. An overdue motion emits one step and
schedules the next in the future. The active contact's hold deadline is
separate from any later queued press.

With this change, the HIX 100-pixel jump test scrolls about 100 pixels, as
PIC does with the same delivery code. An SDL event replay delivered
16-pixel steps 139,810 slots apart, the final point 279,620 slots before
release. Queue tests cover late batches, sustained retargeting, reversal,
overdue delivery, full-panel diagonals, exact endpoints, release ordering,
and independent hold times for successive clicks.

The 68k frontend also requests accelerated vsync presentation, matching
DataRover, and falls back to software if unavailable. This addresses host
scanout tearing; it does not make the guest's in-place framebuffer redraws
atomic.

## Host execution overhead

A host profile during an SDL Hallway drag placed about 24% of samples in
the machine loop and 12% in audio servicing. The shared 68k machine used to
service audio and recalculate the interrupt level after every instruction.
Audio now runs at output-sample deadlines or register changes, and
interrupt levels are recalculated when pending sources or enables change.
Guest CPU, timer and audio clocks are unchanged. A 200-million-slot HIX
retained run went from 15.21 to 8.21 seconds with byte-identical RAM and
WAV output; an 80-million-slot Envoy comparison was also identical.

The runtime reports `hix300` and the SDL title is `MagicHat — Sony
HIX-300`; screenshot names use the HIX identity too.

## Audio and battery sensors

A replay reaches a clear Desk and captures guest audio through the shared
engine. The HIX serial helpers read an identity chip, not Envoy-style
battery RAM, so the EconoRAM model is not applied. HIX has its own backup
battery reading and GUI host-charge mapping based on its ROM thresholds.
See [68k parity](68K_PARITY.md).

## PC Link installation path

Tapping the Storeroom computer on HIX MC19 C2 exercises the DUART
channel-B transmit path (SIM offsets `+0x718..+0x71B`). The guest emits
repeated, valid-FCS asynchronous PPP frames containing a `Cnct` GMTP
command, which rules out "HIX uses another serial channel".

HIX's transmitted PPP protocol `0x0021` frames start with a
length-prefixed link record and 24 metadata bytes before GMTP, rather than
the PIC-2000 UDP/IPv4 envelope. Its ROM *receive* path, however, requires
ordinary UDP/IPv4 with IP protocol 17: the ROM class inventory names
`GMTPOverPPPLink`/`GMTPOverPPP`, and `GMTPOverPPP_HandlePDU` checks for
protocol 17. The host PC Link parser (`src/host/pclink.c`) accepts the HIX
transmit envelope and replies with UDP/IPv4 PPP frames. The guest no longer
stops at "The communications service is not available." The first captured
record includes `Cnct` and the owner name `First Last`.

HIX acknowledges short runs of outgoing GMTP frames cumulatively, so its
send window is three frames; PIC keeps a one-frame window. HIX may also
piggyback multiple GMTP PDUs and PC Link commands in one frame, and the
host parser consumes each PDU and decodes the combined command stream.

In a `Counter.pkg` trial the ROM reached `Send` and acknowledged through
the final `SndX` frame, but did not answer the completion ping. By the
300-million-instruction timeout the guest was in an address-error loop with
a blank framebuffer, and PC Link still reported `sending Counter`. This is
not a successful installation. A 20-million-instruction control run from
the same retained state, with the same Storeroom tap and no transfer, still
displayed the Storeroom. See [68K_NETWORKING.md](68K_NETWORKING.md) for the
PIC-2000 PC Link route.

## Remaining work

- Diagnose the address-error loop after the full PC Link package stream is
  acknowledged; the package is not yet installed.
- Verify the audio divider against stronger evidence; successful startup
  does not establish its clock accuracy.
- Check ordinary Desk interactions and touch alignment beyond onboarding,
  and establish the countdown timer's terminal-count semantics.
- Investigate undecoded accesses on page `80000000`. Code near `0E063A00`
  obtains a pointer from RAM `BBC` and writes dispatch history through it;
  this is not enough evidence to map a new peripheral.
- Establish battery, power, auxiliary latch, identity-chip and accessory
  behavior beyond boot and calibration.
- Explain the ROM checksum mismatch; recovery only bypasses it.
