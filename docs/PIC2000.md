# PIC-2000 and the 68k board

The Sony PIC-2000 was the first 68k target, and its board model is shared
by HIX-300 and Motorola Envoy with board-specific differences (see
[HIX300.md](HIX300.md) and [ENVOY.md](ENVOY.md)). It boots from a cold
start through touch calibration to the Desk. No schematic or board
datasheet is available: everything below is read from the ROM's own
behavior and the MC68349 User's Manual, and the code in
`src/machines/pic2000` and `src/soc/mc68349` is the authority where they
disagree with this page.

![PIC-2000 touch-to-begin screen](images/pic2000-touch-to-begin.png)

```sh
./build/mhat --rom roms/PIC-2000.rom
# Headless: 60M instructions, then dump the framebuffer
./build/mhat --rom roms/PIC-2000.rom --headless --fresh --temporary \
  -n 60000000 --dump 2800,38400,fb.bin
```

The framebuffer is 480x320, 2 bits per pixel, 120 bytes per row, 38,400
bytes, at `0x00002800` in ordinary DRAM; unpack four pixels per byte, most
significant bits first. `--dump` takes its length in decimal.

## The 68k ROMs

All are exactly 4 MiB and begin with a reset vector pair (initial
supervisor stack, initial PC). The reset code is nearly identical across
devices: load SP from `$0E000212`, clear A0, `move.l a0,usp`, then load a
hardware base.

| ROM | Reset PC | ROM base | Device record |
| --- | --- | --- | --- |
| Sony PIC-1000 | `0E000202` | `0x0E000000` | `1,1.0,SONY,1,` |
| Sony PIC-2000 | `0E00021E` | `0x0E000000` | `1,1.5,SONY,2,` |
| Sony HIX-300 | `0E0000C2` | `0x0E000000` | `1,0.19,SONY,1,` |
| Motorola Envoy 1.0 | `02400216` | `0x02400000` | `1,1.0,MOTO,1,` |

The version is the device record `<type>,<version>,<VENDOR>,<model>,`, not
the `Magic Cap 1.0 CIS` string, which names the CompuServe service. The
PIC-2000 carries `1,1.5,SONY,2,` twice and one `1,1.0,SONY,2,`. See
[ROM_DETECTION.md](ROM_DETECTION.md) for how the launcher uses these.

## Processor: MC68349 with a CPU32+ core

The reset path executes `movec` (DFC, VBR) and `moves`, which rule out a
68000, and programs a System Integration Module with chip selects from
+0x40: the 68340/68349 signature. The MC68349 manual identifies the core
as CPU32+ within its CPU030 subsystem.

- **MBAR.** The reset path sets DFC to 7 (CPU space) and writes the module
  base with `moves.l d0,$3ff00.l`; the value is `3C0001BB`, so the module
  space sits at `0x3C000000`. CPU space is modeled as its own address
  space, not a memory region (`src/soc/mc68349/bus.h`), and the module
  region follows MBAR. Any other CPU-space access is counted and reported.
- **IDR.** MBAR+$002 is the read-only identification register. MC68349
  returns `$31` (manual section 4.3.2.2); zero identifies an MC68340. The
  ROM tests it at `0E000252` and ORs `$80` into the clock setting for the
  MC68349, selecting SYNCR `$CF83` instead of `$CF03`. With IDR reading
  zero the ROM also programs CS0 with a mask that cannot decode its own
  4 MB ROM.
- **Clock.** Section 4.3.3 gives
  `Fsystem = Fref x 2^(2W + X + 3Z - 1) x (Y + 1)`. With the documented
  32.768 kHz reference, `$CF83` (W=1, X=1, Y=15, Z=1) gives **16.777216
  MHz**; `$CF03` would give 2.097152 MHz. A long startup-to-Desk replay
  records exactly one SYNCR write, `$CF83`, at instruction `0E00025C`. The
  physical reference crystal and clock-mode straps are unverified.
- **Odd instruction addresses fault.** The ROM deliberately jumps to odd
  tagged addresses: dispatch tables hold entries such as `0xC10033F1`, and
  the address-error handler at `0E08877A` checks the faulting instruction
  against `0x284`, the `JMP (A0)` of the RAM dispatch trampoline, and
  interprets the address. A core that allows the odd fetch executes
  garbage. The project core raises vector 3, builds the CPU32+ 24-byte
  format-C frame whose return PC and fault address name the odd
  destination, and supports RTE from it (manual sections 5.6.2.3,
  5.6.2.12 and figure 5-19). Tens of thousands of address errors in a
  normal run are this mechanism working, not faults.
- **User-mode time reads.** `move.w sr,d0` at `0E08F718` is privileged on
  CPU32; user threads asking the time take a privilege violation that the
  handler at `0E08F7C8` emulates. These are also normal.
- **No FPU.** The ROM contains `frestore`, `fmove` and `fmovecr`, and a
  software 68881 emulator at the line-F handler `0E1230B8`, which reads the
  instruction back out of the format-0 frame. CPU32 has no coprocessor
  interface, so these always trap. Do not add an FPU to the model.
- **LPSTOP idle.** The idle instruction at `0E08FAA0` is `F800 01C0 2000`,
  CPU32 `LPSTOP #$2000`. The CPU stops and wakes on an eligible interrupt.
  A settled Desk waits at `0E08FAA6`.

See [M68K_CORE.md](M68K_CORE.md) for the core itself, and
[M68K_PERFORMANCE.md](M68K_PERFORMANCE.md) for how idle time is skipped.

## Memory map

The chip selects the PIC-2000 ROM programs at reset (mask, then
base/control):

| Chip select | Mask | Base/control | Use |
| --- | --- | --- | --- |
| CS0 | `01FFFFF4` | `0E0000F9` | ROM at `0x0E000000` |
| CS1 | `7FFFFFF1` | `8000FFF1` | not identified |
| CS2 | `23FFFFFF` | `040000F1` | second RAM bank at `0x04000000` |
| CS3 | `000001F5` | `0C0000F1` | `dev0c` register block at `0x0C000000` |

| Address | Region |
| --- | --- |
| `0x00000000` | Boot overlay of the ROM until CS0 is programmed, then DRAM |
| `0x04000000` | Second RAM bank (XRAM); slot 1 common memory while a card is seated |
| `0x08000000` | Decoded, floating test-image slot; slot 2 common memory while a card is seated |
| `0x0C000000` | `dev0c` register block (CS3); HIX-300 uses `0x1E000000` |
| `0x0E000000` | 4 MiB ROM |
| `0x21000000` | `dev21` register file |
| `0x24000000`, `0x2C000000` | PC Card attribute windows, slots 1 and 2 |
| `0x28000000`, `0x30000000` | PC Card I/O windows (ROM-declared) |
| `0x3C000000` | MC68349 module space (per MBAR) |

A 68300 boot chip select answers the whole address space out of reset, so
the vector pair is fetched from address 0. The overlay is retired when the
ROM writes CS0's base (`+044 = 0E0000F9`) and restored on power-on.

Low DRAM must exist and reach at least 2 MB: the reset path loads its
stack from `*(0x0E000212)` = `0x00080000` and a warm-boot base from
`*(0x0E0000A0)` = `0x00200000`. At `0x04000000` the ROM looks for the
longword `'XRAM'` (`0x5852414D`) when choosing its stack; that test alone
does not decide heap recovery, since a valid low-RAM restart block is also
accepted. The ROM never sizes DRAM (coverage is identical at 1, 2, 4 and
8 MB); `--ram` sets the modeled size, 4 MB by default, still unmeasured.
At `0x08000000` the ROM looks for `'TEST'`/`'test'` and, if found, jumps
into a development image; an empty, floating region is the ordinary case.

Writes to ROM succeed on the bus but are discarded, as on hardware; the
machine reports them, because a run can otherwise show zero undecoded
accesses while throwing writes away. Envoy's ROM additionally appears at
`0x00400000` ([ENVOY.md](ENVOY.md)). The card windows are in
[STORAGE.md](STORAGE.md) and [68K_NETWORKING.md](68K_NETWORKING.md).

## MC68349 modules

- **SIM**: MCR `4081`, SYNCR `CF83`; chip selects as above.
- **DUART** (module `+0x700`): channel B carries PC Link; channel A is the
  modem port (`--serial a`, `--net user`). See
  [68K_NETWORKING.md](68K_NETWORKING.md). The serial module is initialized
  with its own CPU-vectored interrupt, outside the `dev21` tables.
- **DMA channel 2** (`+0x7A0`): Magic Bus transfers; status at `+0x7AA`
  is write-one-to-clear. See [PIC2000_MAGICBUS.md](PIC2000_MAGICBUS.md).
- Other modules are disabled or stopped at reset (writes to `+0x780`,
  `+0xC10..C1C`, `+0xFC0`), and remain unmodeled.

## dev21

`0x21000000` is a register file of an unidentified ASIC:

| Offset | Role |
| --- | --- |
| `40` | LCD control; bit 4 enables the display. The frontend shows black while it is clear. |
| `48` | Framebuffer base in four-byte units; zero means the PIC default `0x2800`. HIX programs `2000` (RAM `0x8000`). |
| `4E..61` | Audio ([PIC2000_AUDIO.md](PIC2000_AUDIO.md)) |
| `90..A0` | Magic Bus serial transmitter and receiver ([PIC2000_MAGICBUS.md](PIC2000_MAGICBUS.md)) |
| `B0/B4`, `B2/B6`, `BA/C2`, `B8/C0` | Interrupt pending/enable groups (pending is write-one-to-clear) |
| `D0` | Physical inputs; a zero word write requests power-off (ROM `0E088F36` waits at `0E088F88`) |
| `D1` | Inputs: bit 1 is `HardwareOptionKey`, bit 6 Envoy's AC adapter |
| `D4` | 32-bit free-running counter, 128 Hz |
| `D8` | One-shot timer compare |
| `DC/DE` | Pen sampling countdown (8 ms units) and its enable |
| `E0/E4` | ADC control and conversion (start by write, sample by read) |
| `E6/E7` | Serial one-wire line (Envoy EconoRAM, HIX identity chip) and Envoy accessory input |
| `EE` | Status inputs: PC Card detect, ready, lock and battery bits |

**Interrupt groups.** The service routine at `0E0889FE` sets up group 1:
handler table at RAM `0x0510`, pending at `B0`, enable four bytes later,
and bit number starting at 30, so the pending bit of table entry k is
`30 - k`. The other groups have tables at `0x0608` (from bit 7, pending
`BA`, enable `C2`, `0E088A30`) and `0x0648` (from bit 27, pending `B8`,
enable `C0`, `0E088EAA`). The OS enable mask `0x010C3002` is bits 1, 12,
13, 18, 19 and 24, entries 29, 18, 17, 12, 11 and 6: every one has a
registered handler and no entry without one is enabled. Pending registers
are write-one-to-clear: every one-shot writer masks a source out of the
enable register and then writes exactly those bits to pending, and the
ADC poll at `0E07A1D2` writes `0x50` and then waits for those bits. Only
modeled sources drive the interrupt line.

**Counter and timer.** Every reader of `D4` takes the safe double read of
a ripple counter and scales by 125/16 (`0E08F6F8`, `0E08F718`); every
deadline writer scales the other way (`0E085764`, `0E08CA4C`).
Battery-life accounting at `0E07A310` uses 3,600,000 units per hour, so
the unit is milliseconds and the counter runs at **128 Hz**. `D8` is
written with interrupts masked from the head of a sorted timer list
(`0E08CE8C`, `0E08D0FC`). Table entry 17 is `0E08CDDC`, which walks the
expired timers and reprograms the compare, so **the timer is pending bit 13
on IPL5**.

**ADC.** `ReadAtoDChannel` at `0E07A128` writes `0x23` to `E0`, delays,
clears completion bits `0x50` in `B2`, writes `channel << 6` to `E4`,
polls `B2`, and averages four reads of `E4` (10-bit samples). Only bit 6
is modeled as completion; the pen path names it specifically. Battery
servers read channels 2 (main) and 4 (backup); the model supplies fixed
832 and 512, above the ROM's full thresholds of 805 and 487 observed at
`0E07A2D6` (HIX uses 640 for backup; see [68K_PARITY.md](68K_PARITY.md)).
Zero means a missing battery. The pen converts twice under mux `0x69`,
selecting the axis by channel; readings are latched when a conversion
starts.

**Pen.** The digitizer is group-1 bit 1 (entry 29, handler `0E08B75C`),
and the model raises it on both pen-down and pen-up; without the release
edge, controls pressed but never ran their command. The countdown at
`DC` expires on group-1 bit 14, handled at `0E08B730`. A held reading of
133 or more is accepted, 17..132 is rejected as noise, and four readings
of 15 or less end the touch. The raw-to-screen transform is at
`0E08BDA8`, and `QueueInput` (selector `0x073E`) receives each touch at
`0E08C0DC`. Pen contact must not assert `D1` bit 1, which is the Option
key. `--tap at,len,x,y` resolves screen pixels through the ROM's current
calibration endpoints in RAM.

**Power.** The PIC-2000 power button is momentary (F4 in the GUI,
`--power-at` headless); the shutdown path at `0E088F36` masks IRQs and
repeatedly clears `D0` until power is removed. HIX latches its power input
([HIX300.md](HIX300.md)).

## dev0c

`dev0c` at `0x0C000000` (CS3) is powered by the boot code when `dev21+EE`
reports bits 6 or 7, setting bits such as `0x100` and `0x200` and spinning
`0x1E000` iterations after each. Byte `+2` bit 2 is the Magic Bus accessory
input ([PIC2000_MAGICBUS.md](PIC2000_MAGICBUS.md)). The rest of the block
is a reported register file.

## Timing

`--cpi` sets the cycles-per-instruction approximation used to convert
retired instructions into elapsed time, default 1. At four cycles per
instruction the ROM's timer work became overdue and the input task never
returned from `CheckPendingRun(1)`; at one it drains and calibration
proceeds. The Envoy's one-wire battery RAM is timed from the core's cycle
count instead ([M68K_CORE.md](M68K_CORE.md)). The pen countdown is
converted in its own 8 ms units rather than through the 128 Hz counter.

## Unresolved

- `dev21+010..037` looks like a five-entry memory write-protection region
  file: `+012` is hot, bracketing the dispatch trampoline at `0x28A` with
  unprotect/store/reprotect. Not modeled.
- The SIM's periodic interrupt timer is set up (PICR `+022 = 061A`, level
  6 vector `0x1A`; handler `0E08F6D6`) but arms with period zero.
- `move.l ($0DFFE612).L,d1` at `0E08F82E` reads an unmapped address; the
  other 68k builds read `*(0x0E000212) - 0x1C00` there, so this looks like
  a mis-assembled operand in the PIC-2000 build.
- CS1's decode, the audio and pen ASIC identities, RAM sizes, and bus
  error recovery beyond odd instruction fetches.
